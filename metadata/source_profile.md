## 8. Hand-written notes

### Source and ownership
- Dataset: Spotify Tracks Dataset on Kaggle, created by Maharshi Pandya (https://www.kaggle.com/datasets/maharshipandya/-spotify-tracks-dataset).
- Prior work: this lab reproduces the group project "Mood versus Technical Audio Features in Predicting Spotify Track Popularity" (Aguaviva, Aguirre, Tolentino), Predictive Analytics, Mapua University.
- License as shown on the Kaggle page: ODbL for the database, with "Database Contents" terms for the individual records.
- Redistribution decision: the raw CSV is NOT committed to GitHub. The repository holds a source manifest, the expected filename, the SHA-256 checksum, and the placement convention `data/source/dataset.csv`.
- Update frequency: unknown. The file is treated as a static, immutable snapshot, so the checksum is the version check.

### Identifiers and keys
- `Unnamed: 0` is the original row number (0 to 113,999). It is unique and increasing. It is not business data, so it will serve as the stable source row key and the ordering for batches.
- Business key: `track_id`. It is NOT unique in the raw file: 24,259 rows repeat an earlier `track_id` (the same track listed under several genres).
- 16,641 `track_id` values appear more than once, and 720 of them have different `popularity` values across their rows. Keeping the "first" row therefore changes the data, so rows must be ordered by `Unnamed: 0` before duplicates are removed.
- Even (`track_id`, `track_genre`) repeats in 450 rows, so that pair is not a clean key either.

### Timestamps and incremental processing
- The dataset has no event or update timestamp.
- Incremental ingestion will be a laboratory simulation: deterministic batches by `Unnamed: 0`, with the last completed batch as the checkpoint. This is not a natural business watermark (Section 4.3).

### Leakage and non-feature fields
- `popularity` is the target. A `popularity_tier` derived from it must never be used as a model input; it is used only to stratify the split, as in the baseline.
- `track_id`, `artists`, `album_name`, `track_name` are identifiers or metadata and are excluded from model features.
- `duration_ms`, `explicit`, and `track_genre` are not model features in the baseline (the model uses the 12 audio features only).

### Schema and data-quality risks
- One row (`Unnamed: 0` = 65900, genre k-pop) has null `artists`, `album_name`, and `track_name`. The baseline drops it.
- `tempo` = 0 in 157 rows and `time_signature` = 0 in 163 rows. These look like placeholder values. The baseline kept them, so the contract will warn about them rather than reject them.
- `duration_ms` = 0 in 1 row.
- The file has 114 distinct `track_genre` values, but the group report says 125 genres. This is a documentation discrepancy to explain in the reproducibility report.
- Column types are inferred when the file is read, so explicit types will be declared in the data contract.
